# Per-applet attestation — W25

```mermaid
sequenceDiagram
  participant F as Trusted personalisation station / offline CA
  participant C as Applet (ETH2, MuSig2 or vault)
  participant H as Host / enrolment verifier
  C->>C: At install: native P256 identity + random instance ID
  F->>C: Read identity; initialise PIN, VERIFY, one-shot KEYGEN
  C->>C: Prepare NHWV1 signature; atomically publish key + binding
  F->>F: CA signs NURI-ATT-V1 certificate message
  F->>C: STORE_ATTESTATION_CERT once, read back, SEAL, read back
  H->>H: Independently pin CA, issue fresh challenge32
  H->>C: GET_ATTESTATION page 0 and page 1, same challenge
  C-->>H: Certificate/identity + signed current key/PIN state + NHWV1
  H->>H: Verify CA, AID, expected key, response, binding; consume challenge
```

## What this proves, and what it does not

The intended statement is **“a key generated inside a card our CA personalised”**.
This relies on the CA operator installing/reviewing this applet on physically
trusted hardware, checking its identity, and not certifying software substitutes.
It is **not chip certification**. **CA key custody is the trust root.**

| Boundary | Established by this implementation | Not established |
|---|---|---|
| Applet identity | Separate native P-256 key pair is generated at each install. No identity scalar-import, scalar-export, debug or reset APDU exists. | A Java Card key object is not independent evidence of the chip model, manufacturer PKI or resistance to extraction. |
| Certificate | Pinned Nuri CA signs versioned domain, random instance ID, canonical AID and identity pubkey. Offline verification checks this signature. | A compromised/misused CA can certify an emulator. The certificate does not identify an Infineon/NXP batch or bind a CPLC value. |
| Card ID | Random 16-byte **applet-instance** ID. Each of the three applets has its own identity. | A shared physical-card ID or proof that three certified applets reside on the same chip. |
| Money key | ETH2 and MuSig2 generate the signing key internally. NHWV1 is prepared at KEYGEN and committed with the public cache/keyed flag. A fresh response also binds the currently committed key. | Host/FIDO2 credential enrolment, a 2-of-3 server policy, or proof of firmware/applet hashes. FIDO2 attestation and cross-applet credential-ID binding are not added here. |
| Vault | A separate native P-256 **binding key** is generated by authenticated one-shot KEYGEN. | Vault HMAC/bearer slots are imported by the owner. This does **not** attest that imported secrets were generated on-card, nor make bearer values non-exportable. The binding key is not an EVM spending key. |
| Freshness | Host issues random32, verifies the response against it, enforces an age limit, and consumes it. Saved CLI state is locked and consumed even for failed signature verification. | A card clock, prevention of live relays, or freshness if an administrator restores old challenge state. Stateless `verify_response` requires a caller-owned freshly issued challenge. |
| PIN state | Signature covers required/set/validated/blocked flags. ETH2 is mandatory by default; an unconfigured mandatory applet returns `6982` to SIGN/KEYGEN. | A fresh physical approval per signature, a display, or encrypted PIN transport. APDUs remain plaintext. |
| Certificate seal | Certificate bytes are write-once; explicit applet seal permanently disables storage. Trusted personaliser checks exact readback. | **The seal flag itself is not in the specified signed messages.** A remote verifier cannot cryptographically prove irreversible sealing; its seal check is a policy check, not a signed lifecycle assertion. |
| Firmware lifecycle | Applet seal is irreversible within the installed applet. | GlobalPlatform lock, immutable code, anti-rollback or protection against GP-authorised deletion/reinstall. Those remain separate launch gates. |
| Runtime | jCardSim tests, independent Java/Python verification, native-host fakes, popup tests and two byte-identical CAP builds. | Real-card P-256/native-ECDSA availability, memory/latency, physical tears, fault/side-channel resistance, HSM PKCS11 interoperability, or Chrome-on-card testing: **UNVERIFIED** by W25. |

The popup wording **“genuine Nuri card”** is shorthand for the configured
CA/app-key checks above, not a product certification. It appears only in `card`
mode and only for boolean `attestation.verified === true`. Missing CA pin,
legacy applet, simulator or any failed check remains unverified. The native
host deliberately does not block ordinary info/signing because attestation is
unconfigured or unavailable; relying enrolment services must require verified
attestation themselves.

## Curve and implementation provenance

Identity keys and CA use **NIST P-256**, native Java Card
`Signature.ALG_ECDSA_SHA_256` over complete messages, DER signatures. P-256 is the
existing FIDO2-class native curve; this avoids adding software scalar arithmetic
or relying on custom secp256k1 support for vault identity signing. ETH2/MuSig2
money keys remain secp256k1. Unsupported native primitives fail installation;
there is no software identity-key fallback. Target-batch support is still
UNVERIFIED until parent acceptance.

This is a clean-room protocol/implementation. Keycard's 98-byte format and
Bitkey's HWV1 idea were references only; no Keycard, Satochip or Bitkey code was
copied. This is **not** their certificate encoding. Python reuses the repository's
existing `python-ecdsa` dependency; no new runtime dependency was added.

The canonical helper is [`card/attestation/NuriAttestation.java.in`](../card/attestation/NuriAttestation.java.in).
[`generate-attestation.py`](../scripts/generate-attestation.py) emits identical
package-local implementations, because independent CAP packages cannot import
an uninstalled shared Java Card package. `--check` rejects stale copies.
Transient message/signature/reply buffers clear on every command exit and
selection change. No private scalar is copied into attestation scratch.

## Wire protocol

Canonical AIDs: ETH2 `4E5552494554483201`, MuSig2 `4E5552494D554701`,
vault `4E555249564C5401`. Installation rejects a different instance AID.
CLA is `80` for ETH2/vault and `00` for MuSig2; P2 is zero.

| INS | Input | Output / policy |
|---|---|---|
| `70` GET_ATTESTATION_INFO | Empty, P1=0 | INFO below; public, including before KEYGEN. |
| `71` STORE_ATTESTATION_CERT | CA signature DER (8–72 bytes), P1=0 | Once only, before seal. Data and length publish transactionally. Refused forever after storage or seal (`6985`). Trusted first-use provisioning only. |
| `72` GET_ATTESTATION | Challenge32; P1=0 then P1=1 | Page 0 is INFO (certificate included); page 1 is signed tail. Send the **same challenge** on the **same selected session**; concatenate pages for logical evidence. Each response is at most 256 bytes; no extended APDU support is required. |
| `73` SEAL_ATTESTATION | Empty, P1=0 | Irreversible transaction, only after certificate storage; repeat/empty seal refused. Does not lock GlobalPlatform. |
| `74` GET_KEY_BINDING | Empty, P1=0 | Cached NHWV1 DER signature, `6986` before KEYGEN. No regeneration on reads. |

Lengths are unsigned one-byte values; public keys use canonical SEC1 encoding.
All messages are byte concatenations of the ASCII domains shown, with no NUL,
JSON, hex encoding, or hidden prehash step:

```text
CA:       NURI-ATT-V1      || cardId16 || AID || identityPub65
Response: NURI-ATT-RESP-V1 || challenge32 || currentSigningPub || pinState1
Binding:  NHWV1           || AID || newSigningPub

INFO: 01 || cardId16 || aidLen1 || AID || identityPub65 || sealed1
      || certLen1 || certDER
Tail: signingPubLen1 || signingPub || pinState1 || responseSigLen1
      || responseSigDER || bindingSigLen1 || bindingSigDER
Logical evidence = INFO || Tail
```

ETH2/MuSig2 signingPub is compressed secp256k1 pub33. Vault uses uncompressed
P-256 pub65. Before KEYGEN, signingPub and binding are empty (not enrolment-valid).
PIN-state bits: `01` required policy, `02` configured, `04` validated,
`08` blocked. Response signature and NHWV1 are P-256 ECDSA/SHA256 even for a
secp256k1 money key. INFO metadata is authenticated by the CA signature except
for its separately returned `sealed` flag.

The two-page transport avoids jCardSim's short-response `BAD_LENGTH` and
extended-APDU reader assumptions. Page 0 carries immutable certificate metadata;
page 1 has the signed challenge/current key/state. Substitution of identity,
challenge, key or PIN state fails verification. Physical T=0/T=1 procedure
handling still needs parent verification.

## ETH2 and version changes

ETH2 app version **2.1.0**, package **2.1**; MuSig2 app **1.15**, package **2.2**;
vault package **1.1** (its existing four-byte STATUS remains compatible).
The MuSig2 PIN2 nonce/finalize wire format and W20 hardening are unchanged.

ETH2 strict GP application bytes follow MuSig2: empty = mandatory/unset,
`00 || pinLen || PIN` = mandatory/install-personalised, **`01 00`** = explicit
PIN-less public demo. No APDU can enable demo mode later. SET_PIN no longer
logs in; VERIFY is separate. Existing CHANGE_PIN/PUK retry/unblock semantics
remain. Reinstallation generates new keys; this is not a migration of ETH v1.

## Host, CA custody and freshness

- [`nuri_attest.py`](../scripts/nuri_attest.py): strict parser, P-256 CA pin,
  signature/point/AID/key checks, NHWV1, host-issued consume-once challenges.
  CLI supports `challenge` and `verify`; `ChallengeVerifier` is the native
  host's immediate-session API.
- [`attest-card.py`](../scripts/attest-card.py): dry-run personalisation by
  default; real access requires `--execute`. `init-key` is also dry by default,
  refuses configured/keyed/demo/certified/sealed states, obtains PIN/optional
  ETH2 PUK through a controlling terminal, and does SET_PIN → VERIFY → KEYGEN
  without automatic command replay. A successful KEYGEN is read back and NHWV1
  independently verified; explicit re-SELECT logs out before disconnect.
- Private CA PEM must be owned by the current user, a regular non-symlink file,
  mode **exactly `0600`**, P-256. Never put it inside a checkout, CI artifact,
  log or backup of this repository. Keep the production CA offline/HSM-backed.
- Alternative: `--pkcs11-uri 'pkcs11:object=Nuri-CA;type=private' --openssl
  /opt/homebrew/bin/openssl`; requires an externally configured OpenSSL 3
  PKCS11 provider/authentication. PIN-value URIs are rejected; returned signatures
  are checked against the independent public pin. Actual HSM operation is
  UNVERIFIED; tests use a signer fake, not an invented HSM result.
- `NURI_CARD_CA_PUBKEY` is a **public-key file path**, PEM or SEC1 hex. Configure
  it on the native host process, not just an unrelated shell. The macOS installer
  packages the verifier next to the host and verifies its snapshot checksums.
  When unset, info has `{verified:false, reason:"unverified"}`; never fake true.

## Blank-card personalization

Operator-only procedure on an approved blank spare; simulator-tested, not
physical-card accepted. Never use a funded card or your only SSH key.

Remove the owner's SSH card. The following installs **only these three applets**
on a separately approved blank spare, without deleting anything. It intentionally
does not use the ETH2/vault convenience installers, whose existing FIDO2 presence
precondition is unsuitable for a truly blank card. The parent owns FIDO2/GP-lock
integration and `provision-card-v1.sh`; W25 does not edit that script or README.

Use a trusted terminal and a production CA that already exists **outside** the
repository. Do not manufacture a new CA just to make verification turn green.

```sh
set -euo pipefail
: "${SPARE_GP_READER:?set approved blank-spare GP reader name}"
: "${SPARE_READER_NAME:?set matching PCSC reader name}"
: "${NURI_CA_KEY:?set external mode-0600 P256 CA PEM path}"
: "${NURI_CARD_CA_PUBKEY:?set independently pinned CA public-key file}"
PY="${PYTHON_BIN:-python3}"
export NURI_READER="$SPARE_READER_NAME"
umask 077
EVIDENCE="$(mktemp -d "$HOME/nuri-attestation-acceptance.XXXXXX")"
# Parent inspects both outputs and confirms this is the authorised blank spare.
gp -r "$SPARE_GP_READER" -i
gp -r "$SPARE_GP_READER" -l
# STOP if it is not blank or any of these package/AIDs already exists.
(cd dist && shasum -a 256 -c SHA256SUMS)
gp -r "$SPARE_GP_READER" --install dist/nuri-eth2-signer.cap
gp -r "$SPARE_GP_READER" --install dist/nuri-musig2-v20-keygen.cap
gp -r "$SPARE_GP_READER" --install dist/nuri-vault.cap
gp -r "$SPARE_GP_READER" -l

for aid in 4E5552494554483201 4E5552494D554701 4E555249564C5401; do
  # PIN is prompted twice; ETH2 may additionally use --with-puk.
  "$PY" scripts/attest-card.py init-key --aid "$aid" --execute \
    > "$EVIDENCE/$aid-key.json"
  "$PY" scripts/attest-card.py info --aid "$aid" --execute \
    --out "$EVIDENCE/$aid-info.bin"
  # Dry run: signs public identity evidence only, no reader connection/write.
  "$PY" scripts/attest-card.py personalize --aid "$aid" \
    --info-file "$EVIDENCE/$aid-info.bin" --ca-key "$NURI_CA_KEY" --seal
  # Explicit write-once store + irreversible APPLET seal with exact readback.
  "$PY" scripts/attest-card.py personalize --aid "$aid" \
    --info-file "$EVIDENCE/$aid-info.bin" --ca-key "$NURI_CA_KEY" --execute --seal
  pub="$("$PY" -c 'import json,sys; print(json.load(open(sys.argv[1]))["signing_pub"])' \
    "$EVIDENCE/$aid-key.json")"
  "$PY" scripts/nuri_attest.py challenge --state "$EVIDENCE/$aid-state.json" \
    --expected-aid "$aid" --expected-signing-pub "$pub" --out "$EVIDENCE/$aid-challenge.bin"
  "$PY" scripts/attest-card.py capture-response --aid "$aid" --execute \
    --challenge-file "$EVIDENCE/$aid-challenge.bin" --out "$EVIDENCE/$aid-response.bin"
  "$PY" scripts/nuri_attest.py verify --state "$EVIDENCE/$aid-state.json" \
    --response-file "$EVIDENCE/$aid-response.bin" > "$EVIDENCE/$aid-verified.json"
done
```

Complete each challenge/capture/verify within 60 seconds; a failed/expired or
second verification consumes/refuses that state. Issue a **new** state/challenge
for a new attempt, never restore the old file. PIN/keygen failures are not
retried automatically. If a provisioning write is uncertain, stop and inspect
public state; do not repeat KEYGEN or guess PINs. This helper deliberately does
not repair partially provisioned cards. GP locking and real signature/host
reader regressions follow under parent control; applet sealing is not GP lock.
